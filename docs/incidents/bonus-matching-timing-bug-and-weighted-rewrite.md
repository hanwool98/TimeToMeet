# 추가대화 연속 동일 상대 재매칭 사고 분석 및 매칭 알고리즘 전면 개편

**작성일**: 2026-09-27
**대상 서비스**: 타임투밋(TimeToMeet) — 오프라인 로테이션 소개팅 행사 운영 웹앱
**범위**: 추가대화(보너스 라운드) 상태 전이 순서, 추가대화 매칭 알고리즘 전체

> 참가자 실명·연락처·닉네임 등 개인정보와 운영 DB의 실제 ID/secret은 이 문서에 포함하지 않았습니다. 등장하는 수치는 전부 이번 작업 중 실제로 실행한 시뮬레이션 테스트 결과입니다.

## 1. 문제 상황

테스트 행사에서 추가대화1과 추가대화2를 연속 진행했는데, **같은 두 참가자가 추가대화1과 추가대화2에서 연속으로 다시 매칭**되는 일이 실제로 발생했습니다. 서비스 원칙상 "직전 대화 상대와 바로 다음 회차에서 다시 매칭하지 않는다"는 절대 규칙(HARD CONSTRAINT)이 있었고, 코드에도 이를 지키는 로직이 이미 존재했습니다. 즉 "규칙이 없어서" 생긴 문제가 아니라 "있는 규칙이 조용히 무력화된" 문제였습니다.

## 2. 원인 분석 — "코드는 맞는데 순서가 틀렸다"

먼저 코드를 고치지 않고 운영 DB를 직접 조회해 root cause부터 확정했습니다.

- 문제가 된 두 라운드의 타임스탬프를 비교한 결과, **추가대화1의 "대화 완료 기록" 시각과 추가대화2의 "생성 시각"이 마이크로초 단위까지 완전히 동일**했습니다. PostgreSQL에서 `now()`는 트랜잭션 시작 시점 값을 고정 반환하므로, 이는 두 이벤트가 **같은 함수 호출(같은 트랜잭션) 안에서 발생했다**는 확정적 증거였습니다.
- 실제 상태 전이 함수(`advance_round_state_if_needed`)의 코드 순서를 추적한 결과:
  1. 다음 추가대화(N+1) 배정을 생성하는 함수를 먼저 호출하고
  2. 그 다음에 `event_progress`를 갱신 — 이 갱신이 트리거를 발동시켜 **직전 추가대화(N)의 "대화 완료" 기록을 그제서야 세팅**하는 순서였습니다.
- "직전 상대 제외" 하드 제약은 "대화 완료로 기록된" 상대만 걸러내는 조건이었기 때문에, **다음 회차를 계산하는 바로 그 순간에는 직전 회차가 아직 DB상 "완료되지 않은" 상태**였습니다. 결과적으로 직전 상대 제외 조건이 모든 후보 쌍에 대해 항상 거짓으로 계산되어, 하드 제약이 있으나 마나 한 상태로 전락했습니다.
- tier/fallback 로직 자체(규칙, 우선순위, 완화 단계)는 문제가 없었습니다 — **입력값(직전 라운드가 끝났다는 기록)이 계산 시점에 아직 존재하지 않았던 것**이 root cause였습니다.

## 3. 1차 수정 — 실행 순서만 교정

알고리즘은 전혀 건드리지 않고, "다음 회차 생성"과 "직전 회차 완료 기록"의 순서만 바꿨습니다.

- 기존: `다음 추가대화 생성 → event_progress 갱신(완료 기록 트리거 발동)`
- 수정: `event_progress 갱신(완료 기록 트리거 발동) → 다음 추가대화 생성`

`event_progress` 갱신은 라운드 번호를 바꾸지 않으므로 "다음 회차 번호" 참조는 그대로 유효했고, 다른 세션에는 트랜잭션 커밋 전까지 중간 상태가 노출되지 않아 안전했습니다. 실제 사고 재현 조건(체크인 미완료 1명 포함 7:8 인원)으로 동일한 상황을 재구성해 검증한 결과, 직전 상대 재매칭이 확실히 사라졌고, 연쇄로 추가대화2→3까지 이어지는 경우와 stage가 최종선택까지 정상 도달하는 것도 함께 확인했습니다.

## 4. 근본 재설계 — 매칭 알고리즘 자체를 weighted assignment 문제로 전환

순서 교정으로 사고는 해결됐지만, 기존 매칭 알고리즘은 tier 1~4 + 여러 단계의 강제 선배정(Phase A/A2/A3)으로 구성되어 있어 구조가 복잡했고, "직전 상대 제외"가 추가대화-추가대화 전환에만 적용되고 **정규 마지막 라운드 → 추가대화1 전환에는 적용되지 않는** 별도의 구멍도 함께 발견했습니다. 이 기회에 매칭 원칙을 다시 정하고 알고리즘을 전면 개편했습니다.

### 우선순위 재정의

1. **행사는 절대 멈추지 않는다** (계산 실패가 stage stuck으로 이어지면 안 됨)
2. **정상 인원이면 전원 배치가 필수** (8:8 → 8쌍, 7:8/8:7처럼 성비가 다르면 min(남,여)쌍 + 나머지 휴식은 정상)
3. **직전 라운드 상대만 하드 제외** (그 이전 라운드 상대는 재매칭 허용 — 기존의 "과거 어떤 추가대화에서든 만난 적 없음" 조건은 폐기하고 범위를 명확히 좁힘)
4. **정규 라운드 최저점 상대 재매칭은 소프트 제약** — 가능한 한 피하되, 전원 배치를 위해 필요하면 최소한으로 허용
5. **동률이면 상호 호감도가 좋은 조합 선택**

### 수학적 근거

직전 라운드 배정 자체가 이미 하나의 매칭(서로소 쌍 집합)이므로, 이를 제외한 그래프는 Hall의 결혼 정리 조건을 항상 만족합니다(임의의 후보 집합이 2명 이상이면 이웃 전체가 유지되고, 1명이어도 최소 1명 이상의 상대가 남음). 따라서 **"직전 상대를 피할 수 없어 완전매칭 실패"라는 상황은 이 구조상 수학적으로 발생할 수 없다**는 것을 증명 형태로 확인한 뒤 구현에 들어갔습니다.

### 구현

- **주 알고리즘**: bitmask 기반 weighted maximum bipartite matching. 남녀 후보 쌍마다 가중치를 계산해 단일 최적화로 푼다 — 최저점 위반에는 압도적으로 큰 음수 가중치를, 휴식 순환 우선에는 중간 크기 가중치를, 상호 호감도(기존 검증된 공식 재사용)에는 가장 작은 가중치를 부여해 "필요한 만큼만 자동으로 완화"되는 단일 최적화 문제로 정리했습니다. 수동으로 tier를 하나씩 여는 방식은 제거했습니다.
- **안전망**: 위 최적화가 예외나 버그로 실패해도 행사가 멈추지 않도록, 가중치·호감도를 전혀 고려하지 않고 "직전 상대만 제외"라는 하드 제약만 지키는 완전히 독립된 매칭 경로(Kuhn 알고리즘 기반 augmenting path)를 최후 fallback으로 별도 구현했습니다. 무작위 재시도 대신, 항상 성공이 수학적으로 보장되는 결정론적 알고리즘을 선택했습니다.
- 기존 로직 중 "지각 참가자 강제 우선 매칭", "다음 추가시간 상대 선택 우선권" 같은 부가 규칙은 이번 원칙에 포함되지 않아 제거했고, "휴식자 편중 방지"는 강제 선배정 대신 가중치 항목으로 재구현해 유지했습니다.

## 5. 정의를 넓히려다 발견한 반례 — "직전 상대"는 왜 "바로 직전 라운드"여야만 하는가

알고리즘을 개편한 뒤, "직전 상대"의 의미를 "바로 직전 라운드 상대"에서 "각 참가자가 실제로 가장 최근에 대화한 상대"로 넓히는 방향을 검토했습니다. 언뜻 더 엄격하고 합리적인 정의처럼 보였습니다 — 누군가 한 회차를 쉬었다고 해서 그 직전 상대와의 "방금 나눈 대화"가 없었던 일이 되는 건 아니니까요.

하지만 코드를 고치기 전에 4번 섹션의 수학적 근거를 다시 짚어봤습니다. 완전매칭이 항상 가능하다는 증명은 **"제외되는 쌍들이 그 자체로 하나의 matching(한 사람당 최대 1개, 서로 겹치지 않음)"이라는 전제**에 의존하고 있었는데, "바로 직전 라운드"라는 정의는 이 전제를 공짜로 만족시켜 줍니다(한 라운드의 배정 자체가 원래 매칭이므로). 반면 "각자의 가장 최근 상대"로 넓히면, 사람마다 "가장 최근"을 가리키는 라운드 번호가 서로 달라지므로 이 전제가 더 이상 자동으로 성립하지 않습니다.

실제로 최소 반례를 만들어 검증했습니다: 남 2명(A, B) · 여 2명(X, Y)에서, A는 정규 마지막 라운드에서 X와 만난 뒤 다음 회차를 쉬었고, B는 그 다음 회차에 X와 만났다고 하면 — **A의 "가장 최근 상대"도 X, B의 "가장 최근 상대"도 X**가 되어 X 한 명이 동시에 두 남성 모두에게 "제외 대상"이 됩니다. 그 결과 2×2에서 가능한 두 가지 완전매칭({A-X,B-Y}와 {A-Y,B-X}) 모두 막혀 **완전매칭 자체가 존재하지 않는 상황**이 만들어집니다. 이걸 실제 함수와 안전망 양쪽에 그대로 입력해보니, 예상대로 2쌍이 아니라 1쌍만 생성되는 것을 직접 확인했습니다.

정상적인 8:8 인원에서도 발생할 수 있는 이 구조적 위험을 확인한 뒤, 정의를 넓히지 않고 원래의 "바로 직전 라운드"(정규·추가대화 구분 없이) 정의를 그대로 유지하기로 확정했습니다. 대신 최저점 동점자를 고르는 tie-break은 `random()`에서 `score asc, round_number asc, ratee_application_id asc`(같은 점수를 가장 먼저 준 라운드 우선, 그래도 같으면 완전히 결정론적) 기준으로 바꿔, 같은 데이터로 재계산해도 항상 같은 결과가 나오도록 개선했습니다.

## 6. 최종 검증

전 단계 모두 운영 DB에 대해 `BEGIN`으로 시작해 실제 RPC(`advance_round_state_if_needed`, `generate_bonus_round_assignments`, 안전망 함수)를 그대로 호출한 뒤 `ROLLBACK`으로 되돌리는 방식으로 검증해, 실제 데이터에는 어떤 영향도 남기지 않았습니다.

- 1차 순서 수정: 8:8/7:8 정상 케이스, 실제 사고 재현 케이스, 추가대화1→2→3 연쇄 전환, bonus_round_count 소진 후 최종선택 전환까지 **전부 직전 상대 재매칭 0건**, stage stuck 없음 확인.
- 2차 알고리즘 개편: 정상 8:8, 최저점이 다양하게 분포된 경우(0-penalty 매칭 탐색), **여성 8명 전원이 같은 남성 1명을 최저점으로 선택한 극단적 상황**(그래도 8쌍 전원 배치 유지, 불가피한 최소 위반 1건만 발생), 상호 최저점 쌍이 여러 개 존재하는 경우(둘 다 회피해 위반 0건 달성), 7:8·8:7 불균형(휴식자가 다음 회차엔 다른 사람으로 교체되는 순환 확인), 안전망 단독 단위 테스트(56개 후보 중 완전매칭 성공) 등 8개 시나리오 **전부 통과**.
- 반례 발견 이후 최종 확정판: 정규마지막→bonus1→bonus2 전 구간 8:8 유지, 7:8·8:7 각각의 휴식자가 "바로 직전 라운드"만 피하고 그 이전 상대와는 재매칭 허용됨을 확인, **7:8에서 휴식했던 참가자가 다음 회차에 복귀해 8:8이 되는 경우까지 포함**해 전부 8쌍 완전매칭과 재매칭 0건 확인, 결정론적 tie-break이 동일 데이터 3회 재계산에서 항상 같은 대상을 선택함을 확인.
- 전체 과정에서 **직전 상대 재매칭 0건**을 모든 시나리오에서 유지.

## 7. 배운 점

- **"규칙이 코드에 있다"와 "규칙이 실제로 작동한다"는 다르다.** 하드 제약 자체는 처음부터 존재했지만, 그 제약이 참조하는 상태값(대화 완료 기록)을 세팅하는 시점과 제약을 평가하는 시점의 순서가 어긋나면서 제약이 조용히 무력화됐다. 트리거처럼 "부수효과로 상태를 세팅하는" 구조는 그 부수효과가 실제로 언제 반영되는지를 호출 순서까지 추적해야 한다.
- **타임스탬프가 완전히 같다는 사실 자체가 강력한 진단 도구가 될 수 있다.** 두 이벤트의 시각이 마이크로초까지 동일하다는 것은 우연이 아니라 "같은 트랜잭션"이라는 구조적 증거이고, 이걸 실마리로 삼아 코드를 순서대로 추적하는 것이 로그를 뒤지는 것보다 훨씬 빠르고 확실했다.
- **"완전매칭이 항상 가능한가"는 감이 아니라 증명으로 확인해야 한다.** Hall의 결혼 정리를 직접 적용해 "직전 상대 하나만 제외하면 완전매칭은 항상 존재한다"를 증명한 뒤 구현하니, 안전망을 포함해 알고리즘의 정답성 자체를 자신 있게 말할 수 있었다.
- **"더 엄격한 규칙"이 항상 "더 안전한 규칙"은 아니다.** "직전 상대"를 "각자의 가장 최근 상대"로 넓히는 건 언뜻 더 정확해 보였지만, 그 확장이 기존 증명의 전제(제외 집합이 매칭 구조를 이룸)를 깨뜨린다는 걸 실제로 최소 반례를 만들어보고서야 확신할 수 있었다. 요구사항을 구현하기 전에 "이게 기존 안전성 증명과 충돌하지 않는가"를 먼저 검증하는 습관이, 배포 후에야 발견됐을 회귀를 사전에 막아줬다.
- **안전망은 주 알고리즘과 실패 지점을 공유하면 안 된다.** 최적화 로직이 실패했을 때 쓸 fallback을 같은 복잡한 조인/계산 위에 얹으면 같이 무너질 수 있으므로, 가장 단순하고 결정론적으로 정답이 보장되는 별도 코드 경로로 분리했다.

## 8. 면접용 30초 설명

실제 운영 중이던 소개팅 행사에서 같은 두 참가자가 추가대화 두 회차 연속으로 다시 매칭되는 사고가 발생했습니다. 원인은 매칭 규칙 자체가 아니라, "직전 회차가 끝났다"는 기록을 남기는 코드가 "다음 회차를 계산하는" 코드보다 늦게 실행되는 순서 버그였고, 타임스탬프 비교로 원인을 확정한 뒤 실행 순서만 교정해 즉시 해결했습니다. 이어서 기존의 복잡한 다단계 tier 매칭을 Hall의 결혼 정리로 완전매칭 존재를 수학적으로 증명한 weighted bipartite matching으로 전면 개편했고, 그 과정에서 규칙을 더 엄격하게(각자의 실제 마지막 상대 기준으로) 넓히려다 오히려 완전매칭이 불가능해지는 반례를 직접 구성해 발견하고 사전에 되돌렸습니다.

## 9. 면접용 2분 설명

타임투밋은 정규 라운드가 끝나면 참가자들이 조금 더 이야기하고 싶은 사람과 "추가대화"를 이어가는 서비스입니다. 여기엔 "직전 대화 상대와 바로 다음 회차에서 다시 매칭하지 않는다"는 절대 규칙이 있었는데, 실제 행사에서 같은 두 사람이 연속으로 다시 매칭되는 사고가 발생했습니다.

먼저 코드를 고치지 않고 운영 DB의 타임스탬프만 비교해서 원인을 확정하는 것부터 시작했습니다. 문제가 된 두 회차의 "대화 완료 기록 시각"과 "다음 회차 생성 시각"이 마이크로초까지 완전히 같았는데, PostgreSQL에서 같은 트랜잭션 안의 `now()`는 항상 같은 값을 반환한다는 점을 근거로, 두 이벤트가 같은 함수 호출 안에서 일어났다는 걸 확정할 수 있었습니다. 실제 코드를 추적해보니, "다음 회차 배정을 생성하는" 코드가 "직전 회차 완료를 기록하는" 코드보다 먼저 실행되고 있었고, 직전 상대 제외 규칙은 그 완료 기록이 있어야만 작동하는 구조였습니다. 두 코드의 실행 순서만 바꾸는 최소 수정으로 사고를 즉시 해결했습니다.

이 조사 과정에서 기존 매칭 알고리즘이 tier 1~4와 여러 단계의 강제 선배정으로 꽤 복잡하게 얽혀 있고, 정규 라운드에서 추가대화1로 넘어가는 경계에는 애초에 직전 상대 제외가 적용되지 않는 별도의 구멍도 발견했습니다. 이 기회에 알고리즘 자체를 다시 설계했는데, "직전 상대 하나만 제외하면 완전매칭이 항상 존재한다"는 걸 Hall의 결혼 정리로 직접 증명한 뒤, 최저점 회피는 매우 큰 페널티로, 호감도는 작은 가중치로 표현해서 하나의 weighted bipartite matching 문제로 통합했습니다.

여기서 흥미로운 부분이 하나 더 있었는데, 개편 이후 "직전 상대"를 "바로 직전 라운드 상대"에서 "각자가 실제로 가장 최근에 대화한 상대"로 더 엄격하게 넓히자는 요청이 있었습니다. 언뜻 더 정확한 정의처럼 보였지만, 코드를 먼저 고치는 대신 이 변경이 앞서 세운 수학적 증명의 전제를 깨뜨리지 않는지부터 점검했습니다. 실제로 최소 반례(2명씩 4명, 한 명이 쉬는 사이 그의 옛 상대가 다른 사람과 만난 경우)를 직접 구성해보니, 그 사람 한 명이 동시에 두 사람 모두에게 "제외 대상"이 되면서 정상적인 인원에서도 완전매칭이 아예 불가능해지는 상황을 발견했고, 실제 함수와 안전망 양쪽에 넣어 정말로 매칭이 덜 나오는 것까지 확인했습니다. 이 반례를 근거로 정의 확장은 되돌리고, 대신 최저점 동점자를 고르는 기준만 무작위에서 결정론적인 규칙으로 개선했습니다.

검증은 정규 마지막 라운드부터 추가대화 전 구간, 극단적인 최저점 분포, 인원이 쉬었다가 복귀하는 경우까지 운영 DB에서 직접 시뮬레이션했고, 모든 경우에서 직전 상대 재매칭 0건과 전원 배치를 확인했습니다. 이번 일로 얻은 가장 큰 인사이트는, 요구사항을 "더 엄격하게" 만드는 것이 항상 "더 안전하게" 만드는 것은 아니며, 그 변경이 기존에 세워둔 안전성 증명과 충돌하지 않는지 배포 전에 직접 반례로 검증하는 과정이 꼭 필요하다는 것이었습니다.

## 10. 이력서/포트폴리오 Bullet

- 실제 운영 중이던 소개팅 행사에서 발생한 "직전 상대 연속 재매칭" 사고를, 코드 수정 없이 타임스탬프 비교만으로 root cause(상태 전이 함수 내 실행 순서 버그)를 확정하고, 최소 범위 수정으로 즉시 해결
- Hall의 결혼 정리를 적용해 "직전 상대 하나만 제외하면 완전매칭이 항상 존재한다"를 수학적으로 증명한 뒤, 기존의 4단계 tier + 다단계 강제 선배정 구조를 단일 weighted bipartite matching으로 전면 재설계
- 최적화 실패 시에도 행사가 멈추지 않도록 가중치와 무관하게 하드 제약만 보장하는 결정론적 안전망(augmenting path 알고리즘)을 별도 코드 경로로 구현
- 배포 전 "직전 상대" 정의를 더 엄격하게 넓히자는 요청에 대해, 기존 수학적 증명의 전제(제외 집합이 매칭 구조를 이룸)가 깨질 수 있음을 최소 반례로 직접 구성·검증해 회귀를 사전에 방지하고, 대신 최저점 tie-break을 결정론적 기준으로 개선
- 운영 DB에 대한 `BEGIN`/`ROLLBACK` 시뮬레이션으로 극단적 성비·평점 분포와 휴식-복귀 시나리오까지 포함한 테스트로 직전 상대 재매칭 0건, 전원 배치 100%, stage stuck 0건을 확인
