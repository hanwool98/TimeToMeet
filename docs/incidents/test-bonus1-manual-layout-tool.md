# 테스트 전용 "첫 추가대화 자리 변경" 도구 설계 및 안전성 보강

**작성일**: 2026-09-27
**대상 서비스**: 타임투밋(TimeToMeet) — 오프라인 로테이션 소개팅 행사 운영 웹앱
**범위**: 테스트 행사 전용 관리자 도구, 추가대화1 배치의 서버 검증/동시성/UI 모델

> 참가자 실명·연락처·닉네임 등 개인정보와 운영 DB의 실제 ID/secret은 이 문서에 포함하지 않았습니다. 등장하는 수치는 전부 실제 실행한 시뮬레이션/동시성 테스트 결과입니다.

---

## 1. 문제 상황

추가대화 매칭 알고리즘(직전 상대 하드 제외, 과거 bonus 상대 회피, 최저점 penalty, baseline 호감도 등)을 여러 차례 손본 뒤, 다음 단계로 넘어가려면 "특정 조합이 실제로 만들어진 상태에서 다음 회차가 어떻게 반응하는가"를 검증해야 했습니다. 매번 정규 라운드부터 다시 진행해 우연히 원하는 조합이 나오길 기다릴 수는 없었기 때문에, **관리자가 추가대화1의 조합을 직접 지정한 뒤 그 상태를 실제 bonus1 기록으로 삼아 이후 알고리즘을 검증할 수 있는 테스트 전용 도구**가 필요했습니다.

## 2. 설계 원칙

- **실제 행사에는 절대 존재하지 않는다.** 버튼 노출뿐 아니라 RPC 자체가 서버에서 `is_test_event` 여부를 검증해, 실제 event_id로 직접 호출해도 거부됩니다.
- **수동 배치는 "임시 미리보기"가 아니라 진짜 bonus1 기록이어야 한다.** 이후 자동 생성기가 되돌리거나 덮어써서는 안 되고, bonus2/3의 "직전 상대"·"과거 bonus 상대" 판단이 자동 생성된 결과와 완전히 동일하게 이 수동 기록을 인식해야 합니다.
- **매칭 알고리즘(가중치, 최저점, baseline, safety fallback)은 전혀 건드리지 않는다.** 이 도구는 알고리즘의 "입력값(직전 상태)"만 사람이 대신 만들어주는 도구이지, 알고리즘 자체를 바꾸는 도구가 아닙니다.

## 3. 1차 구현 — 기존 멱등성 재사용

`bonus1이 언제, 어떻게 생성되는가`부터 코드로 추적했습니다: 관리자가 "재개"를 누를 때 호출되는 함수가 `generate_bonus_round_assignments`를 호출하는데, 이 함수는 **이미 해당 회차 배정이 있으면 즉시 아무 것도 하지 않는 멱등 함수**였습니다. 이 성질을 그대로 활용해서:

- 새 "조회" RPC가 열람 시점에 bonus1이 없으면 그 자리에서 한 번 생성해 보여주고,
- "재개"가 나중에 다시 호출돼도 이미 있으니 절대 재생성/덮어쓰기하지 않는다

는 구조를 만들었습니다. **기존 생성 로직은 한 줄도 수정하지 않고, 그 멱등성이라는 기존 성질만 새로운 용도로 재사용**한 것이 이 설계의 핵심입니다. 저장은 (테이블 번호, 여성)로 고정된 각 행의 남성 ID만 업데이트하고, 검증은 "제출된 남성 목록을 정렬한 배열이 현재 배치와 완전히 동일한 집합인지" 단 한 번의 비교로 중복·누락·비활성 참가자 사용을 동시에 차단하도록 설계했습니다.

## 4. 안전성 보강 — 시간차 공격면 점검

기능이 동작한 뒤, "조회와 저장 사이에 상태가 바뀌면 어떻게 되는가"를 별도로 점검했습니다.

- **Stale roster**: 조회 이후 참가자가 불참 처리되면, 저장 시점에 다시 active roster를 계산해 검증하도록 고쳤습니다 — 예전 목록과 제출값이 일치한다는 이유만으로 이미 무효해진 참가자가 그대로 저장되는 일을 막았습니다.
- **동시 실행**: 이 도구가 상호작용하는 다른 관리자 RPC(재시작, 재개)와 **완전히 동일한 잠금(advisory lock + `event_progress` 행 잠금)을 공유**하도록 만들어, "저장 중 재시작"·"재개와 저장 동시 실행" 같은 경쟁 상태를 막았습니다. 기존 함수는 전혀 수정하지 않고 같은 잠금 키를 재사용하는 것만으로 상호 배제가 성립하도록 설계했습니다.
- 이 잠금이 실제로 동작하는지는 **두 개의 독립된 DB 커넥션**으로 직접 검증했습니다 — 한쪽이 잠금을 잡고 6초간 점유하는 동안 다른 쪽이 실제로 약 9초간 블로킹된 뒤에야 진행되는 것을 확인해, 순차 시뮬레이션이 아니라 진짜 동시성 보호가 작동함을 증명했습니다.

## 5. 2차 확장 — 남/여 불참을 하나의 모델로

타임투밋은 **여성 고정 좌석 / 남성 순환** 구조라서, 남성이 부족한 경우(7:8)와 여성이 부족한 경우(8:7)는 의미가 다릅니다. 여성은 항상 고정 테이블이 있으므로 "이번 회차만 상대가 없는 것"으로 표현되지만, 남성은 애초에 고유한 테이블이 없으므로 "어느 테이블에도 없는 상태"로만 표현할 수 있습니다.

먼저 "여성의 고정 테이블 번호는 어디서 authoritative하게 가져오는가"부터 코드로 확인했습니다 — 실제 배정 결과(파생 데이터)가 아니라, 행사 시작 시 딱 한 번 생성되는 **원본 좌석 배정표**가 유일한 근거였습니다. 체크인 여부와 무관하게 참가 확정자 전원의 좌석이 여기 담겨 있어, "지금 대화가 없는 여성의 테이블"이나 "아예 불참한 여성의 테이블"도 화면에서 사라지지 않게 만들 수 있었습니다.

이걸 바탕으로 세 가지 경우(8:8, 7:8, 8:7)를 **하나의 모델**로 통합했습니다: "활성 여성 수만큼의 테이블 슬롯" + "그 슬롯을 채우는 활성 남성 풀". 남성이 모자라면 슬롯 하나가 자연스럽게 비고(7:8), 남성이 남으면 풀 밖으로 빠져 별도의 "휴식 남성" 목록이 된다는 식으로, 두 가지 서로 다른 불참 상황을 별도 UI/로직 분기 없이 같은 자료구조로 표현할 수 있었습니다. 여성이 아예 불참한 테이블은 이 모델에서 완전히 제외해 "여성 불참, 배치 불가"로 별도 표시하고 절대 편집 대상이 되지 않게 했습니다. 저장 검증도 "테이블 집합 일치 + 남성 중복 없음 + 남성이 현재 활성 집합의 부분집합 + 배치 인원 수 = min(활성 남/여)" 네 가지 조건만으로 세 경우 모두를 하나의 로직으로 커버하도록 다시 짰습니다.

## 6. 배포 직전 — 저장 방식 전환(UPDATE → DELETE+INSERT)의 참조 안전성 점검

7:8/8:7 지원을 위해 저장 로직을 "행 단위 UPDATE"에서 "기존 추가대화1 행 전체 DELETE 후 재INSERT"로 바꾸면서, 이 방식은 각 배정 행의 `id`가 매번 새로 생성된다는 부작용이 있었다. 배포 직전에 이 부작용이 실제로 안전한지 코드베이스와 운영 DB 스키마를 직접 조회해 확인했다.

- **다른 테이블이 이 행의 `id`를 참조하는가**: 운영 DB의 `information_schema`에서 이 테이블을 참조하는 foreign key를 전수 조회한 결과 0건. 신고, 키워드 미션, 하트노트 등 관련 기능은 전부 `event_id + round_number + 참가자 application_id` 조합으로 이 테이블을 조회하지, 배정 행의 `id` 자체를 저장하거나 참조하지 않는다는 것을 마이그레이션 코드에서 직접 확인했다.
- **기존 행의 메타데이터(생성 시각, 미션 노출 시각, 대화 완료 시각)를 잃어도 되는가**: 이 도구는 "추가대화가 아직 시작되지 않은" 단계에서만 동작하도록 서버에서 이중으로 막혀 있어(관리자 화면 진입 조건 + RPC 내부의 진행 단계 하드 체크), 그 시점의 배정 행은 애초에 이 메타데이터가 전부 비어 있는 상태임을 확인했다. 즉 DELETE+INSERT로 "잃는" 값이 실제로는 존재한 적이 없다.
- 결론: 참조/부작용 없음을 확인해 DELETE+INSERT 방식을 그대로 유지하고 배포했다.

## 7. 검증

운영 DB에 대해 `BEGIN`으로 시작해 실제 RPC를 그대로 호출한 뒤 `ROLLBACK`으로 되돌리는 방식으로 검증했으며, 실제 두 커넥션을 이용한 진짜 동시성 테스트를 제외하면 모두 실제 데이터에 영향을 남기지 않았습니다.

- 8:8: 테이블 8개, 휴식 0, 남성 자리 교환 정상 저장
- 7:8(남성 불참): 활성 여성 테이블 8개 전부 표시, 정확히 1개 휴식 표시, 휴식 테이블 변경 후 pair 7 유지
- 8:7(여성 불참): 활성 여성 테이블 7개 + 불참 테이블 별도 표시, 휴식 남성 1명 표시, 휴식 남성 배치 변경 후 pair 7 유지
- 불참 여성 테이블에 배치 시도, 조회 이후 참가자 불참 처리 후 저장 시도 → 모두 서버에서 정확한 사유로 거부
- 재시작 → 현재 roster 기준으로 재조회 → 재편집 정상 동작
- 수동 bonus1 → bonus2: 직전 상대 재매칭 0건, 정책 그대로 유지

## 8. 배운 점

- **기존 멱등성은 새 기능을 만들 때 재사용할 수 있는 자산이다.** "이미 있으면 아무 것도 안 한다"는 성질 하나를 이해하고 나니, 생성 로직을 전혀 건드리지 않고도 "미리 만들어서 편집 가능하게 하되 나중에 자동 생성기가 되돌리지 않는다"는 새로운 요구사항을 만족시킬 수 있었다.
- **"기능이 동작한다"와 "안전하다"는 별개의 검증이다.** 정상 경로가 통과한 뒤에도 "그 사이에 뭔가 바뀌면?"이라는 질문을 별도로 던져야 stale 데이터 저장이나 경쟁 상태 같은 문제를 찾을 수 있었다. 특히 잠금의 존재를 코드로 확인하는 것과 실제로 블로킹이 일어나는 것을 두 커넥션으로 직접 재현해 증명하는 것은 신뢰도가 전혀 달랐다.
- **도메인의 비대칭성을 인정하면 모델이 단순해진다.** "여성 고정, 남성 순환"이라는 서비스의 근본 구조를 무시하고 남녀를 대칭적으로 다루려 했다면 7:8과 8:7을 각각 별도 로직으로 처리해야 했을 것이다. "슬롯(여성 고정) + 풀(남성 순환)"이라는, 실제 도메인 구조를 그대로 반영한 모델을 택하니 두 불참 케이스가 자연스럽게 하나의 로직으로 통합됐다.
- **저장 방식을 바꿀 때는 "무엇을 잃는가"부터 확인한다.** UPDATE를 DELETE+INSERT로 바꾸면 행의 식별자(`id`)가 바뀐다는 사실은 기능 테스트만으로는 드러나지 않는다. 배포 전에 "이 id를 참조하는 곳이 있는가"를 스키마 레벨(FK 전수 조회)과 코드 레벨(조인 방식 확인) 양쪽에서 직접 확인하고 나서야 안전을 주장할 수 있었다.

## 9. 이력서/포트폴리오 Bullet

- 테스트 전용 관리자 도구를 설계하며 기존 함수의 멱등성을 그대로 재사용해, 생성 로직을 전혀 수정하지 않고도 "미리 만들어 수동 편집 → 이후 자동화가 덮어쓰지 않음"이라는 요구사항을 충족
- 조회~저장 사이의 stale roster/동시 실행 경쟁 상태를 자체 점검해, 기존 관리자 RPC와 동일한 잠금(advisory lock + row lock)을 공유하는 방식으로 회귀 없이 보강 — 실제 두 DB 커넥션으로 블로킹을 직접 재현해 증명
- "여성 고정 / 남성 순환"이라는 도메인 구조를 반영한 "슬롯 + 풀" 모델을 설계해, 남성 부족/여성 부족이라는 서로 다른 두 불참 케이스를 하나의 UI·검증 로직으로 통합
