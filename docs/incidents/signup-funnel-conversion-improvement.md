# 광고 유입 신청 전환율 개선 (신청 동선 간소화)

**작성일**: 2026-09-24
**대상 서비스**: 타임투밋(TimeToMeet) — 오프라인 로테이션 소개팅 행사 운영 웹앱

> 참가자 실명·연락처 등 개인정보와 운영 DB의 실제 ID/secret은 이 문서에 포함하지 않았습니다.

## 1. 문제 상황

메타(Facebook) 광고를 통해 홈페이지로 들어오는 방문자 대비 실제 행사 신청 완료 건수가 낮았습니다. 신청 과정을 다시 살펴보니, 광고로 막 들어온 신규 방문자가 실제 신청(프로필 작성)을 시작하기까지 다음을 전부 거쳐야 했습니다.

- 후기 이미지가 원본 비율 그대로 표시돼 화면이 매우 길어지고, 정작 신청 버튼은 스크롤을 해야 보임
- "행사내용 확인" 페이지를 반드시 거쳐야 신청 버튼에 도달
- 전화번호 입력 → PIN 설정 → PIN 재입력의 별도 "비회원 계정 만들기" 화면

## 2. 원인

| 증상 | 원인 |
|---|---|
| 신청 화면 첫 화면에서 버튼이 안 보임 | 후기 이미지가 원본 비율(세로로 긴 스크린샷)로 렌더링 |
| 신청 시작까지 화면 전환이 많음 | CTA가 "행사소개"를 강제로 거치게 설계됨 |
| 신규 방문자가 프로필 작성 전에 이탈 | 실제 신청과 무관한 "계정 생성" 단계가 별도 화면으로 분리돼 있었음 |

## 3. 해결

- **후기 이미지**: 이미 있던 참가자 대표사진 크롭 렌더러(`ParticipantPhoto`/`RepresentativeCrop`)를 재사용해 고정 비율(3:4) 박스로 통일. 관리자 콘텐츠 관리 화면에 있던 이 섹션만의 "크롭 없음" 예외를 제거하고 확대/위치조정 편집기를 그대로 열어줌.
- **CTA 구조**: "1분만에 프로필 작성하기"(행사소개 건너뛰고 바로 프로필 작성) + "행사내용 확인하고 계속하기"(기존 경로 유지) 2단 버튼으로 재구성.
- **계정 생성 자동화**: 프로필 작성 화면에서 이미 입력받는 전화번호+생년월일이 채워지는 즉시, 백그라운드에서 비회원 계정을 자동 생성(초기 PIN = 생년월일 6자리). 별도 "계정 만들기" 화면 없이 신청 흐름이 끊기지 않음. 이미 가입된 번호면 생년월일 추측 로그인을 시도하지 않고 기존 로그인 화면으로 안내(계정 탈취 방지).

## 4. 기술적 의사결정

- 계정 생성을 **제출 시점이 아니라 입력 초반**(전화번호+생년월일 확정 시점)으로 당김 — 그래야 기존 프로필 임시저장(draft) 보호가 폼 작성 내내 걸려서, 중간 이탈에도 입력 내용이 안전함.
- 생년월일 PIN이 기존 계정과 충돌하면(이미 가입된 번호) **추측 로그인은 시도하지 않고** 항상 기존 로그인 화면으로 안내 — 실제 PIN이 생년월일이 아닐 수 있고, 짐작 시도가 로그인 제한 횟수만 소모시킬 수 있어서.
- 새 인프라를 만들지 않고 전부 기존 것 재사용(크롭 렌더러, `create_guest_session` RPC, DB unique 제약) — DB/Edge Function 변경 없이 프론트엔드만으로 완결.

## 5. Before / After

| 항목 | Before | After |
|---|---|---|
| 신청 시작까지 화면 수 | 신청화면 → 행사소개 → 계정 만들기(3단계 입력) → 프로필 작성 | 신청화면 → 프로필 작성 |
| 후기 이미지 높이 | 원본 비율(가변, 매우 김) | 고정 3:4, 참가자 리스트 영역과 비슷한 높이 |
| 계정 생성 | 별도 화면, 수동 PIN 설정 | 프로필 작성 중 자동, 생년월일 기반 초기 PIN |

## 6. 결과 (실제 검증한 것)

- Playwright로 실제 사용자 플로우 검증: 신청화면 → 메인 CTA → 로그인 화면 없이 프로필 작성 화면 도달, 전화번호+생년월일 입력 후 자동 계정 생성(예: 생년월일 1998-06-18 → PIN 980618 정상 생성) 확인.
- 이미 가입된 번호 입력 시 추측 로그인 없이 안내 문구만 노출되고 재시도 스팸 없음(정확히 1회만 시도) 확인.
- 390px 모바일 뷰포트에서 후기 박스 높이 약 392px로 축소, CTA 버튼이 스크롤 없이 화면 안에 위치함을 좌표로 확인.
- 운영 DB에 대해 실제 신규 참가자 흐름(계정 자동 생성 → 나머지 프로필 작성 → 임시저장 → 새로고침 후 복원 → 실제 제출)을 테스트 행사로 끝까지 실행해 신청서가 정상 저장되고 임시저장이 정리됨을 확인(테스트 후 생성한 데이터는 전부 정리함).

## 7. 배운 점

- 전환율 문제는 알고리즘이 아니라 "화면 개수"인 경우가 많다 — 계정 생성이라는, 사용자 입장에서 신청과 무관해 보이는 단계 하나가 이탈 지점이 될 수 있다.
- 이미 만들어둔 인프라(크롭 렌더러, 세션 발급 RPC)를 재사용하면 새 마이그레이션 없이도 UX를 크게 바꿀 수 있다.
- 편의 기능(자동 PIN)을 추가할 때는 항상 "기존 사용자를 보호하는 조건"을 먼저 정의하고(계정 존재 시 추측 로그인 금지 등), 그다음에 새 사용자 편의를 설계해야 한다.

## 이력서 Bullet

- 광고 유입 방문자의 신청 이탈 지점을 분석해, 계정 생성 단계를 신청 폼 내 자동 처리로 통합하고 CTA/후기 이미지 레이아웃을 개선 — 신청 시작까지 필요한 화면 수를 4단계에서 1단계로 축소, 기존 사용자 보호 장치(계정 중복 생성 방지, 추측 로그인 차단)를 유지하면서 프론트엔드만으로 구현
